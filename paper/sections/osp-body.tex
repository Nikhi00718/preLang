\section{Motivation and significance}

Much of the hidden cost of machine-learning systems sits in their data dependencies and glue code rather
than in the models~\cite{sculley2015}. A large share of that glue is data preparation: a script over
pandas~\cite{mckinney2010} or OpenCV~\cite{bradski2000} that finds out only at run time whether the column it
scales holds numbers, or whether the pixels it saves as PNG are floats. Validators such as
TFDV~\cite{breck2019}, Deequ~\cite{schelter2018}, Great Expectations~\cite{gx} and pandera~\cite{bantilan2020}
check the data, yet they never look at the code that transforms it.

Batch preparation offers something a compiler can rarely count on: the input is already on disk when the
pipeline is compiled. \PL reads it. Where F\# type providers infer types from a sample~\cite{petricek2016},
\PL takes values from every CSV cell, every Parquet footer and every image header, and carries what it
learns (column types, missing values, numeric ranges, image sizes and channels) from one statement to the
next. Each contract is proven or refuted before any row is processed, and checks or operations that the
input makes pointless are removed.

A proof about this month's file does not carry over to next month's, even when the layout is unchanged.
For each removal, \PL therefore records the facts it relied on, the removal's \emph{item certificate}, and
the generated program tests them against every new batch. While they hold, the removal stands. When a batch
breaks them, the removed code runs again for that batch, much as dynamic compilers fall back from
optimized code~\cite{holzle1992,barriere2021}; we call this \emph{selective deoptimization}. A numeric
column may also switch between whole and decimal numbers from one batch to the next, provided that
compiling with the other type yields the same program, and the column is then read with whatever type the
batch has. A batch is refused only when no run-time code can recover a fact, for instance when a numeric
column arrives as text. A user compiles a \texttt{.prep} program against the batch at hand and deploys the
generated program for the batches that follow.

Table~\ref{tab:related} sets \PL against the closest tools. Validators see the values but check them away
from the code, on every batch; static analyses follow the code but see only declared or inferred structure.
We know of no other tool that decides value contracts at each point of a program from the real data and
carries those decisions forward to later batches.

\section{Software description}

\subsection{Software architecture}

The compiler (\texttt{src/}, about 11{,}800 lines of C++17 with no external libraries) is a conventional
pipeline of lexer, LL(1) parser, semantic analysis, IR, optimizer, certifier and code generator
(Fig.~\ref{fig:arch}). Its schema readers scan CSV files in parallel and read only the footers of Parquet
files and the headers of PNG and JPEG images. The semantic analyzer builds an abstract state of each dataset
(types, missing values, value intervals, image properties) and decides every contract against it. The
optimizer removes, speculatively, whatever that state shows to have no effect. The certifier then
reanalyzes the program under weaker input facts, without touching the data, to find the admission
certificate and one item certificate per removal. Finally, the back end emits a single Python program that
admits or refuses each batch, guards every removed instruction with \texttt{deopt(i)}, and writes the
certificates to \texttt{preplang\_contract.json}.

\input{figures/figure-arch}

\texttt{proofs/} holds \LeanLines{} lines of
Lean~4~\cite{lean4} that prove two results: for any sound and monotone analysis, the generated program
agrees with a fresh compilation on every batch it admits; and the analysis of a core of the language is
sound and monotone. Joins, groups, dates and images fall outside that core. The differential test of
Section~\ref{sec:impact} covers joins and groups, while dates and images are covered only by unit tests and
the examples. \texttt{tests/} contains \TestCount{} checks in \TestSuites{} suites.

\PL can be installed with \texttt{pip} or run from the \texttt{Dockerfile}, and each release ships prebuilt
compilers for Windows, Linux and macOS. A VS Code extension (\texttt{editors/}) shows the diagnostics when
a file is saved. Continuous integration builds and tests the compiler on three systems (Windows with MSVC,
Ubuntu and macOS with GCC), compiles every example, runs the tests under AddressSanitizer and
UndefinedBehaviorSanitizer with a coverage gate, fuzzes the three parsers of untrusted input
(\texttt{.prep}, CSV, Parquet footers) with libFuzzer, and checks the Lean proofs. \texttt{LANGUAGE.md}
documents the syntax, the command-line options and the generated program, and \texttt{ARCHITECTURE.md}
maps each phase to its source files.

\subsection{Software functionalities}

{\sloppy
\begin{itemize}
\item \textbf{Compile-time checking.} Misspelled or dropped columns, type errors and broken contracts
(\texttt{NOT\_NULL}, \texttt{BETWEEN}, \texttt{UNIQUE}, \texttt{REFERENCES}, schemas, image channels and
sizes, match rates between images and labels) are reported with the line, an offending row and a hint, as
are joins on keys of different types. A lookup join expects each key once, while \texttt{JOIN ... MANY}
keeps every match. Groups (\texttt{AGGREGATE}, with eight functions from \texttt{COUNT} to \texttt{STD})
keep their facts.
\item \textbf{Data-driven optimization.} Proven checks and operations without effect are removed, unread
columns are never loaded, and image pipelines stream one file at a time; rewrites that alter the output
need \texttt{--approx}.
\item \textbf{Tools around the compiler.} \texttt{tools/\allowbreak contracts.py} checks the guarantees of
one compiled stage against the certificates of the next. \texttt{frontend/\allowbreak pandas2prep.py}
translates the cleaning statements of a pandas script into \PL, up to the first statement it cannot express.
With \texttt{--facts}, a program compiles from differentially private facts released by the data owner
(\texttt{tools/\allowbreak release\_facts.py}) without opening any input; since the generated program checks
those facts on the real data, every run is still exact.
\item \textbf{Inspection.} Each phase can be printed (\texttt{--tokens} through \texttt{--python}), along with
an execution plan (\texttt{--explain}) and JSON diagnostics (\texttt{--json}). \texttt{PLOT} draws
histograms and bar, scatter and line charts with matplotlib, marking contract bounds, and \texttt{REPORT}
writes a web page comparing each column of a run with the compiler's view of it.
\end{itemize}
}

\section{Illustrative example}\label{sec:example}

\begin{lstlisting}
LOAD "students.csv" AS students;
EXPECT students.age NUMBER;
EXPECT students.marks BETWEEN 0 AND 100;
EXPECT students.name NOT_NULL;
FILTER students WHERE marks >= 50;
EXPECT students.marks BETWEEN 60 AND 100;
SAVE students AS "clean.csv";
\end{lstlisting}

Compiled against the eight-row \texttt{students.csv} in \texttt{examples/\allowbreak tabular/}, \PL proves
the first three contracts. The fourth stays a run-time check: after the filter, all the compiler knows is
that the marks lie in $[50, 95]$. The range and not-null checks are removed speculatively, and
\texttt{--certificate} lists what the range check depends on, namely marks of at least 0 and at most 100.
Given a later batch that contains a mark of 104, the generated program puts the check back and stops
exactly where a fresh compilation would:
\par\smallskip\noindent\begin{minipage}{\linewidth}\small\begin{verbatim}
Deoptimized line 3: EXPECT students.marks BETWEEN 0 AND 100:
  marks goes up to 104, above 100
ContractError: line 3: students.marks has values outside 0 to 100
\end{verbatim}\end{minipage}\par\smallskip
\noindent A batch that stays within the facts runs with both checks removed. A batch in which \texttt{age}
holds text is refused, because no generated code can stand in for analysing the column under another type.

Image pipelines get the same treatment, from file headers alone. \texttt{examples/\allowbreak images/\allowbreak
linked.prep} links images with their labels, checks them, resizes them, scales the pixels to $[0, 1]$ and
saves NumPy arrays. Switching the output format to PNG produces this error before a single pixel is
decoded:
\par\smallskip\noindent\begin{minipage}{\linewidth}\small\begin{verbatim}
error[type]: cannot save FLOAT32 pixels as PNG:
             NORMALIZE at line 10 scaled them to [0, 1]
   --> examples/images/linked.prep:13:1
13 | SAVE_IMAGES imgs TO "processed/ml_ready/";
   = hint: image files store 8-bit pixels, so these would come out
     almost black; add CONVERT imgs TO NPY; to keep the float
     values
\end{verbatim}\end{minipage}\par\smallskip
\noindent The equivalent OpenCV script runs to completion and writes images that are nearly black.

\section{Impact}\label{sec:impact}

\PL is a research prototype, started in a compiler-design course, and has not yet been used outside the
authors' own experiments. The evidence for it is the evaluation in \texttt{eval/};
\texttt{eval/\allowbreak evaluate.py} derives every number below from the raw results.

\begin{itemize}
\item \textbf{Correctness.} We generated \DiffAll{} random programs over four seeds, with groups, lookup
joins and \texttt{MANY} joins (\DiffMany{} programs). Compiled with and without the optimizer, each produces
the same table, value for value, as an independent Python interpreter of the language that shares no code
with the compiler. Run again on a second random batch, none of the \DiffReuse{} and \DiffSeedReuse{} reuses
disagrees with the interpreter. In \DiffFlipBatches{} of those batches we flipped one numeric column
between whole and decimal values: \DiffFlipRight{} ran or stopped as the interpreter did, \DiffFlipRefused{} were refused
(\DiffFlipNoCompile{} of them could not be compiled at all), and none was wrong. Along the way the test
exposed three bugs: column pruning and a pandas~3 incompatibility, which together made
\DiffBeforeWrongOpt{} optimized runs wrong, and a statistic fill wrongly removed as a dead store
(\DiffSeedBeforeWrong{} run). The CSV fuzzer found a fourth, an out-of-bounds read on a NUL byte. Each fix
has a regression test.
\item \textbf{Performance.} On a 200{,}000-row table the optimized program needs \TabProcOpt\,s instead of
\TabProcOz\,s once Python has started. Most real inputs are far smaller, and over the \CenChanged{} census
programs that the optimizer changes the median speedup is only \CenSpeedMed$\times$ (at most
\CenSpeedMax$\times$). The image pipeline is as fast as a hand-written streaming script and uses
\ImgPlMem\,MiB, against \ImgBaseMem\,MiB for a script that loads every image first.
\item \textbf{Optimization.} Over \CenPrograms{} programs (the examples and the programs lifted from GitHub
scripts), the optimizer cuts \CenInstrCut\% of the instructions (\CenInstrBefore{} to \CenInstrAfter), the
run-time checks from \CenChecksBefore{} to \CenChecksAfter{} and \CenColsCut\% of the columns read. It
changes \CenChanged{} programs, and all \CenSame{} write identical files with and without it. The lifted
scripts carry no contracts, so every removed check comes from the examples or the monthly pipelines.
\item \textbf{Real programs.} Of \RbTotal{} data-preparation bugs reported in GitHub issues, \PL catches
\RbEarly{} at compile time, \RbContract{} of them once the requirement is written down as an
\texttt{EXPECT}. The lifter translates \CorpusBothDerCompiled{} of \CorpusBothScripts{} public scripts
written for the Kaggle Titanic and House Prices data. Their programs match the original script on
\CorpusBothDerSame{} of \CorpusBothDerRuns{} new batches and stop or refuse on the rest; none is wrong.
Among \DriftAll{} traffic and bike-sharing scripts it translates \DriftCompiled{}, and these match the
script on every one of \DriftRuns{} later months of real data. For \DriftNoRead{} of the 945 the lifter
cannot tell which file is read, because the path is known only at run time or the read options change the
table. It also leaves \texttt{!=} and \texttt{\textasciitilde} untranslated: on a missing value pandas keeps
the row, whereas \PL drops it.
\item \textbf{Comparison.} Five monthly pipelines on public data (NYC green taxi, Citi Bike Jersey City, and the UCI
traffic, bike-sharing and Beijing air-quality sets) were each compiled on one month and run on the months
after it. They match a fresh compilation on \RealDeoptCorrect{} of \RealRuns{} months
(\RealDeoptCorrectPct\%) and never produce a different result. That includes the taxi and air-quality months
in which a column switched between whole and decimal numbers, which version~2.0 refused. The Citi Bike and
air-quality pipelines were written for this version, with bounds taken from the domain (the New York area,
physical limits) rather than from the data. Each validator learned from the compiled month as its
documentation recommends (Great Expectations profiles the columns, pandera and TFDV infer a schema) and
was then asked whether the pipeline could run on each later month; its answers were scored against the same
fresh compilation. Great Expectations and pandera reject \RealValidatorStopMax\% of the months, and TFDV
accepts \RealValidatorWrongMax{} months on which the program then gives a different result. These tools were
not designed for this decision, so the figures measure the cost of using them for it. All 24 mistakes injected
into 5 example programs are reported at compile time, while a script-style pandas program crashes on 20
and silently writes wrong output on 4.
\item \textbf{Private compilation.} At $\varepsilon=1$, compiling from released facts keeps every removal in
the taxi and traffic pipelines but only 14\% in the bike pipeline, where AIM~\cite{mckenna2022aim} keeps
54\%. In \PrivTitanicDeoptEpsOne{} of \PrivTitanicScripts{} Titanic compilations a released fact proves
false, and a removal is undone on the very file that was compiled. Across \PrivRuns{} runs, no output
differs from a fresh compilation.
\item \textbf{Overhead.} Compilation takes a median of \CenCompileMed\,ms, most of it spent on the extra
compilations that decide which numeric columns may change type, and never more than \CenMemMax\,MiB of
memory (\CenCsvMillionMem\,MiB for a million CSV rows). Admitting a new batch by its certificate changes
the run time by \OhPctLow\% to \OhPctHigh\%, which is within measurement noise.
\end{itemize}

\noindent \texttt{eval/\allowbreak reproduce.sh check} (about ten minutes, offline, also in Docker) rebuilds
the compiler, runs every test and regenerates these numbers from the committed results; \texttt{full}
(several hours) downloads the inputs, including the GitHub scripts pinned by URL, commit and hash, and
reruns every experiment, and \texttt{baselines} the validators.

\section{Limitations and conclusions}

Joins match on a single key column, and Python is the only target. A numeric column may change type only
if no statement combines it with another column; any other change of type is refused. The mechanized
proofs cover a core of the analysis that leaves out joins, groups, dates and images. Next on the list are
joins on several columns and code generation for other targets.
